# ADR-0004：控制线程与视觉帧率解耦

- **状态**：Accepted
- **日期**：2026-11-13
- **相关代码**：`apps/omni_standard.cpp`、`apps/auto_aim_debug_mpc.cpp`、`include/tools/thread_safe_queue.hpp`

## 背景

两个 app 都是同一套结构：视觉线程只「出目标」，经单槽队列交给控制线程，控制线程是云台唯一写入者。
但控制线程开头是 `auto target = target_queue.front();`——**阻塞**、且不 pop。

于是控制线程的拍频不是代码里写的 10 ms，而是**视觉帧率**：`omni_standard` 的海康链路还要叠加
3 路 USB YOLO，帧率更低，控制线程被拖到十几 Hz。

两个可观测后果：

1. PlotJuggler 里曲线的采样密度随相机帧率变化，`omni_standard` 明显比 `auto_aim_debug_mpc` 稀疏，
   相邻两点被连成直线，看起来像「折线」；
2. MPC 解、`gimbal.send` 指令、开火门控都按视觉帧率刷新，而不是按控制周期。

## 决策

1. 控制线程改用 `try_pop(incoming, 0)` 非阻塞取；取不到就沿用上次快照 `latest_target`。
   队列保持容量 1 + `PopWhenFull`（push 顶掉旧的），所以「队列里最新的那条」就是「最近一次测量」，
   不需要新增 `try_front` 之类的 API。
2. 快照年龄超过 `kTargetStaleS = 0.3 s` 即视为丢目标（视觉线程卡住 / 相机停流），不再拿旧目标规划。
   这不是可选项：解耦之后阻塞读带来的「隐式冻结」消失了，没有这道门就会一直规划一条越来越旧的目标。
3. 每拍重算 MPC，不复用上一次的 `Plan`。`Planner::plan` 内部用 `steady_clock::now()` 做延迟补偿与
   命中时刻预测，复用旧解会让 setpoint 系统性滞后，P 环也会去追一个阶梯信号。
4. 串口下发因此实打实变成约 100 Hz（`Gimbal::send` 无节流）。若实机出现丢帧/看门狗问题，
   再改成「只有新目标才下发 + 心跳兜底」。
5. 发布层顺带对齐：`distance`/`w` 每拍都发（无目标填 0），与 `auto_aim_debug_mpc` 一致；
   新增 `target_age`（快照年龄）与 `plan_ms`（单次 MPC 求解耗时）。

## 被否方案

- **保留阻塞 `front()`，另加定时器/看门狗线程**：仍然无法表达「这一拍没有新测量」，只是把阻塞换个地方。
- **让视觉线程按固定频率重发同一目标**：白跑 YOLO，且下游无法区分「新目标」与「重发的旧目标」。
- **复用上次 `Plan`，只在新目标到达时重算**：setpoint 随视觉帧率阶梯化，位置环仍然在追阶梯。
- **视觉停摆时保持最后一条串口指令（coast hold）**：等于停在一条仍在运动中的旧指令上；
  主动停更安全，而且 `is_empty`/`target_age` 能让上位机看出是「没目标」而不是「没数据」。

## 影响

- 控制与绘图稳定在约 100 Hz，与相机帧率解耦；两次 app 的曲线密度可比。
- `plan_ms` 直接反映 MPC 单次耗时；若持续超过 3 ms（10 ms 预算的 30%），退化为
  「新目标到达时才重算 MPC，中间每拍只跑 P 环 + 前馈」。
- **行为变化**：视觉线程卡住时云台会主动停止，而不是冻结在最后一条指令上（外观上都是「不动」，
  但前者会持续下发 `is_empty=true` 的停止指令）。
