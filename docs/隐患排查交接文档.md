## 1. 接手必读：硬性维护红线

以下约束来自历史踩坑，**改代码前务必先读**：

1. **云台唯一写入者**：`gimbal.send()` 的调用方应只有一个控制线程（`apps/omni_standard.cpp` 已按此重构）。**不要引入异步命令线程**——历史上（对照仓库 `qtl_vision_Omnidirectional_sensing`）异步线程复用旧时间戳曾导致串口通讯乱晃，修复代价很大。
2. **时间戳同源**：相机打点（`hikrobot.cpp` / `usbcamera.cpp` 的 `steady_clock::now()`）、云台姿态历史（`gimbal.cpp` 的 `q_history_`）与上层对齐全部依赖**同一进程内的 `steady_clock` 时钟域**。换硬件时间戳源或改跨进程方案时，`Gimbal::q(t)` 必须同步改造。
3. **`Gimbal::q(t)` 不可回退**：当前实现为 `q_history_` 二分 + slerp 插值（`src/comm/gimbal.cpp:78-116`）。历史 bug：旧实现声明 `t` 却忽略参数、直接返回当前姿态，导致 PnP 姿态与采集时刻错配、串口乱晃；修复提交 `c1cc43e`。**若发现有人"简化"成 `return make_q(state_.yaw, state_.pitch)`，属于严重回退。**
4. **串口协议改动需与电控同步**：`GimbalToVision` / `VisionToGimbal`（`include/comm/gimbal.hpp`）为 packed 结构 + 'S''P' 帧头 + CRC16，改字段必须双方一起改。
5. **标定参数与硬件个体绑定**：`camera_matrix` / `R_camera2gimbal` / `t_camera2gimbal` / `distance_offsets` 是特定相机 + 特定装配的值，换相机/换装配必须重标，不能照抄 yaml。
6. **`Detector` 含帧级复用缓冲，非线程安全**：多线程检测时每线程必须独立实例（`src/omni/perceptron.cpp` 中 detector1_/2_/3_ 的原因）；不要试图共享一份 Detector。
7. **`*_sim.yaml` 只用于无硬件调试**：`simulate: true` 时不开串口、`q(t)` 无历史回退当前姿态——手眼标定等依赖真实姿态的流程**不可用**。
8. **letterbox 缓冲约定**：`image/channel_thresholder` 与 `letterbox` 约定 dst 预清零、只写 ROI 区，调用方负责复用缓冲。改图像预处理时保持该约定（性能主线）。

## 3. 逐条详情

### 3.1【P1】EKF 越界读取 `residual[3]` ✅

- **位置**：`src/tools/extended_kalman_filter.cpp:88`（`update()` 尾部）
- **现象**：`data["residual_angle"] = residual[3];` 无条件执行。当量测维数 ≤ 3 时（`z2` 为 3 维 `xyz2ypd` 结果），`residual` 只有 3 个元素，`residual[3]` 越界。
- **触发路径**：`BuffTarget`（Small/Big）每次 `update()` 的**第二次** `ekf_.update(z2, ...)`（`buff_target.cpp:295` / `:641`），量测为 3 维 → 每次 buff 更新都触发一次越界读。
- **影响**：Release（-O3 + NDEBUG）下静默读到堆上邻接内存（UB），当前表现为 `residual_angle` 绘图值无意义；理论上可因 ASAN / 调试构建断言中断。属"随时可能爆"的地雷。
- **修复建议**（一行级、零风险）：
  ```cpp
  data["residual_distance"] = residual.size() > 2 ? residual[2] : 0.0;
  data["residual_angle"]    = residual.size() > 3 ? residual[3] : 0.0;
  ```

### 3.2【P1】NIS 卡方阈值口径错误，可能过早丢目标 ⚠️

- **位置**：`extended_kalman_filter.cpp:68-69`（`nis_threshold = nees_threshold = 0.711`）；消费方 `tracker.cpp:92-99`。
- **问题**：注释写"自由度=4，置信水平 95%"，但 0.711 实为 $\chi^2(4)$ 的 **5% 下分位**；95% 上分位应为 **≈9.49**。阈值过紧 → `recent_nis_failures` 虚高。
- **连锁影响**：`tracker.cpp` 用"近 100 帧失败率 ≥ 40%"直接判 `Bad Converge` → `state_ = "lost"`，**可能把本来收敛良好的跟踪目标丢掉**（重新进入 detecting 流程，丢失数帧）。
- **当前为什么还能跑**：R/P 设置偏保守，实际 NIS 通常远小于 0.711；一旦目标机动/遮挡导致残差变大，失败会成片累积。
- **验证方法**：跑一局实机，统计日志 `grep -c "Bad Converge Found" logs/*.log`；若频繁出现且肉眼可见跟踪正常，即命中此条。
- **修复建议**：阈值改为 9.488（df=4, 95%）或按实测重新标定；**同时复核** `tracker.cpp` 的 40%/100 帧判据，两者一起调，避免单改一边引发回归。

### 3.3【P1】USB 相机重连计数不重置 → 永久放弃 ✅

- **位置**：`src/camera/usbcamera.cpp:12`（`open_count_(0)`）、`:31`（`if (open_count_ > 20)` → Give up + `quit_ = true`）、`:159`（`try_open()` 内无条件 `open_count_++`）。
- **问题**：`open_count_` 在**每次** `try_open()` 都自增（成功打开也不清零）。守护线程累计 >20 次后：日志 `Give up to open ...`、关闭相机、结束线程——**该相机永久失效，直到进程重启**。
- **触发场景**：USB 供电波动 / 干扰 / 拔插 / 线材接触不良导致取流线程反复退出，守护线程反复重连。全向感知跑长局时，任何一路搜索相机都可能悄悄死掉（不崩溃、无报警、只是那一侧再也搜不到目标）。
- **验证方法**：拔插一路 USB 相机 20+ 次，观察日志出现 `Give up to open` 后该路彻底无输出。
- **修复建议**：成功恢复取流时清零（如取流线程成功读到帧、或 `ok_` 恢复为 true 时置 `open_count_ = 0`）；或把语义改为"连续失败次数"，成功即重置。

### 3.4【P2】`handle_lose()` 状态覆盖 ✅

- **位置**：`src/buff/buff_detector.cpp:69-77`。
- **问题**：先 `status_ = LOSE;`（清 `last_powerrune_`），紧接着**无条件** `status_ = TEM_LOSE;` —— `LOSE` 对外永远不可达，状态机语义被破坏。
- **现状影响**：`status_` 目前仅内部写入、无公有读取接口（全仓 grep 确认），所以实际功能暂未受影响；但这是"埋雷"：任何人后续按 `LOSE` 设计逻辑（如丢失后重置、切换策略）都会踩空。
- **修复建议**：改为 `if (lose_ >= LOSE_MAX) { status_ = LOSE; last_powerrune_ = std::nullopt; } else { status_ = TEM_LOSE; }`，同时明确 `status_` 是否要对外暴露。

### 3.5【P2】全向感知 USB 设备名与安装角错配风险 ⚠️

- **位置**：`configs/omni.yaml`（`omni_usb_devices: ["video0","video2","video4"]`、`omni_usb_yaw_offsets: [60,-60,-180]`）；消费方 `apps/omni_standard.cpp:44-49`、`decider.cpp::delta_angle`。
- **问题**：设备节点名 `videoN` 由内核枚举顺序决定，**插拔顺序变化 / 新增 USB 设备 / 重启后枚举漂移都会改变其对应的物理相机**。一旦 `video0` 不再是装了 60° 方向的那只，`delta_angle` 会用错误安装角算方位 → USB 引导把云台**引向错误方向**（比没有引导更危险）。
- **现状缓解**：代码有索引越界保护；`Perceptron` 对空指针相机会打 error 并静默结束该线程（`perceptron.cpp`），少配设备不会崩溃，但该方向无搜索、主循环无感知。
- **修复建议**：
  - 上机前用 `ls /dev/v4l/by-id/`（或 udev 固定命名）确认绑定关系，配置改用稳定别名；
  - 或在启动时自检：逐路点亮/遮挡验证方向，失败给显式告警。
- **验证方法**：见 §5 清单中"逐一遮挡 3 路 USB"步骤。

### 3.6【P2】TensorRT 硬失败 + 构建硬依赖 ✅

- **位置**：`src/detector/yolos/yolov5.cpp:38-42`（引擎加载失败 `exit(1)`）；`CMakeLists.txt:32-42`（TRT/CUDA 缺失时 `FATAL_ERROR`）。
- **风险**：
  - `.engine` 与 **GPU 架构 / TensorRT / CUDA 版本绑定**，换机或升级后未用 `trtexec` 重导 → 每次启动即退出（`exit(1)` 硬失败，不是降级）。若被 watchdog 守护，会每 5 秒重启一次刷日志。
  - 机器人端（Jetson）没有 TensorRT 时**无法完成 cmake 配置**；README 已给裁剪方案（去掉 FATAL_ERROR 与 `tensorrt_infer.cpp`），但需手动执行。
- **建议**：机器人端部署按 README 裁剪；或把 `exit(1)` 改为回退 OpenVINO 后端并告警（需产品决策）。

### 3.7【P2】`buff_aimer.cpp` 死代码读未初始化变量 ✅

- **位置**：`src/buff/buff_aimer.cpp:36`（`aim()`）与 `:89`（`mpc_aim()`）。
- **问题**：`bool angle_changed = |last_yaw_ - yaw| > 5°...` 在 `yaw/pitch` 被 `get_send_angle()` 赋值**之前**计算，读取未初始化的局部变量，且该变量从未被使用（后续逻辑用的是重新计算的字面表达式）。
- **影响**：UB 温和版（读未初始化 double），无实际功能影响；但会干扰静态分析、误导维护者。
- **修复**：直接删除这两行。

### 3.8【P3】`switching` 状态阈值硬编码 ✅

- **位置**：`src/tracker/tracker.cpp:222`：`if (temp_lost_count_ > 200) state_ = "lost";`
- **问题**：其余路径的丢失上限都来自配置（`max_temp_lost_count` / `outpost_max_temp_lost_count`），唯独 `switching`（全向目标切换流程使用）是魔法数 200，不随配置调整。

### 3.10【P3】`standard_mpc` / `traditional_debug` 双写者竞争窗口 ⚠️

- **位置**：`apps/standard_mpc.cpp`（plan_thread 中 `gimbal.send` + 主循环非自瞄分支的 `gimbal.send`）；`traditional_debug.cpp` 同构。
- **问题**：主循环仅在 `mode != AUTO_AIM` 时发停止命令，正常运行时写入者实际上是 plan 线程；但在**模式切换瞬间**两线程可能先后调用 `send`，存在竞争窗口（`send` 内部有锁，不会数据损坏，但指令顺序不可精确保证）。
- **背景**：`omni_standard` 已重构为**单主循环唯一写入者**（见红线 §1）。若日后有人在旧入口上观察到模式切换瞬间的云台抖动，优先怀疑此处。
- **建议**：新功能一律以 `omni_standard` 的单写者骨架为准；旧入口改造时把 `send` 收敛到单一线程。

### 3.11【P3】相机队列"丢新保旧"语义 ✅

- **位置**：`include/tools/thread_safe_queue.hpp`（默认 `PopWhenFull=false` → 队满时**丢弃新元素**）；相机队列容量 1（`hikrobot.cpp:13`、`usbcamera.cpp:12`）。
- **含义**：消费者偶尔慢时，会读到一帧"更旧"的图像，中间帧被丢弃。对时间对齐链路无害（`q(t)` 按采集时刻插值，旧帧配旧姿态依然自洽），但调试 fps/延迟时别把它当 bug。
- **建议**：保持现状；如需"取最新"语义可换成 `PopWhenFull=true` 并评估。

### 3.12【运维】部署侧注意事项 ✅

- **`-march=native`**（`CMakeLists.txt:12`）：build 产物**不可拷贝**到不同 CPU 的机器使用，部署机须本地全量重编。
- **arm64 SDK 不完整**：`third_party/camera_sdk/hikrobot/lib/arm64` 为旧版且缺传输层库，Jetson 上机前用 MVS 官方 aarch64 包补齐，否则相机枚举失败（`0x80000006`，与 amd64 曾遇到的问题相同）。
- **udev 规则**：海康 USB 权限规则必须配置（README 有命令），否则日志刷 `Unable to open usb!`。
- **watchdog.sh**：
  - `pidof $APP_NAME` 按名字判定，同机运行多个同名/同类程序会互相误判；
  - `MAX_RETRY=100` 达上限后脚本退出（screen 会话仍在但**无守护**）；
  - `cleanup` 的 `pkill -P $$` 只清自己的子进程。
- **日志增长**：screen 日志 + spdlog 按日文件在 `logs/` 无轮转清理，长跑注意磁盘。
- **yaml 里 `use_tensorrt: true` 多处写死**（`omni.yaml`、`standard1.yaml` 等）：机器人端需逐配置改 `false`，漏改会导致 §3.6 的硬失败。

## 4. 已排查排除项（避免重复调查）

### 4.1 海康相机 Bayer→`2RGB` 转换 ≠ bug（**切勿"顺手修"成 `2BGR`**）✅

- **背景**：`src/camera/hikrobot.cpp:138-141` 将 `PixelType_Gvsp_BayerXX8` 映射到 `cv::COLOR_BayerXX2RGB`，而下游（`ChannelThresholder`、`get_lightbar_color`）按 BGR 假设取通道。表面看像通道序 bug。
- **实证结论（本机 OpenCV 4.10 合成 RGGB 马赛克测试）**：
  - OpenCV 的 Bayer 命名与物理图案存在"反转"约定；对物理 RGGB 马赛克，`COLOR_BayerRG2RGB` 与 `COLOR_BayerBG2BGR` **完全等价且还原正确**；
  - 因此 `PixelType_Gvsp_BayerXX8 → COLOR_BayerXX2RGB`（**同名**映射）是正确组合；
  - 若按"直觉"改成 `COLOR_BayerXX2BGR`，反而会**红蓝互换**（左红右蓝场景实测，改后输出错位）。
- **自验方法**（可复现）：
  ```bash
  python3 - <<'EOF'
  import numpy as np, cv2
  scene = np.zeros((40,40,3), np.uint8); scene[:, :20] = (0,0,255); scene[:, 20:] = (255,0,0)
  m = np.zeros((40,40), np.uint8)
  for i in range(40):
      for j in range(40):
          m[i,j] = scene[i,j,2] if i%2==0 and j%2==0 else (scene[i,j,0] if i%2==1 and j%2==1 else scene[i,j,1])
  for n in ["COLOR_BayerBG2BGR","COLOR_BayerRG2RGB"]:
      out = cv2.cvtColor(m, getattr(cv2, n))
      print(n, "左区平均(BGR)=", out[8:32,6:16].reshape(-1,3).mean(0).round(0))
  print("两者应输出相同 -> 当前映射正确；改成同名的 2BGR 则红蓝互换")
  EOF
  ```
